# Wait for Service

The **Wait for Service** node is designed to suspend the execution of your automation flow until a specific computer service (like a system or network service) changes its state to running, paused, or stopped. This feature is particularly useful in scenarios where your automation tasks depend on certain services being in a particular state before proceeding.

For example:

- Before printing, wait for the Print Spooler service to start.
- Before performing database operations, ensure SQL Server is up and running.

## Configuration Options

| Field Name                  | Description                                                                                                                     | Input Type | Required? | Default Value |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ---------- | --------- | ------------- |
| **Wait for Service to**     | Choose the state change to observe: start, stop, or pause the service.                                                          | Select     | Yes       | _(empty)_     |
| **Service Name**            | Select the service you want to monitor. A predefined list of common services is available.                                      | Select     | Yes       | _(empty)_     |
| **Fail with Timeout Error** | If enabled, the node will generate an error if the service does not reach the desired state within the specified duration.      | Switch     | No        | True          |
| **Duration (seconds)**      | Set the maximum number of seconds to wait for the service. This option is visible only if "Fail with Timeout Error" is enabled. | Text       | No        | 30            |

## Expected Output Format

This node does not produce any output values directly. Instead, it suspends the automation process until the specified service status condition is met or until a timeout occurs.

## Step-by-Step Guide

<Steps>
### Step 1

Add the **Wait for Service** node to your workflow.

### Step 2

In the **Wait for Service to** dropdown, select the state change you wish to monitor (Start, Stop, or Pause).

### Step 3

Choose the target service from the **Service Name** dropdown. Select from the list of available services.

### Step 4

Decide if the node should fail if the service doesn't reach the desired state within the specified time. If yes, switch on the **Fail with Timeout Error** option.

### Step 5

If you enabled **Fail with Timeout Error**, define how long the node should wait by entering the number of seconds in the **Duration (seconds)** field.

### Step 6

Proceed with your automation flow; the node will wait as configured for the service state change before continuing.

</Steps>

<Callout type="warning" title="Important">
  Ensure the specified service is configured correctly on your system and that
  you have the necessary permissions to monitor its state. Misconfiguration or
  lack of permissions might cause unexpected behavior.
</Callout>

## Common Mistakes & Troubleshooting

| Problem                                         | Solution                                                                                                    |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **The service never reaches the desired state** | Confirm the service is installed and operational on your system. Check service logs for any startup issues. |
| **"Duration" field not visible**                | Make sure the **Fail with Timeout Error** option is enabled to access the duration setting.                 |
| **Timeout error occurs quickly**                | Increase the **Duration (seconds)** field value to provide more time for the service state change.          |

## Real-World Use Cases

- **System Maintenance**: Wait for critical services to restart post-maintenance before executing dependent tasks.
- **Application Startup**: Ensure application-related services are running before launching the interface or performing data operations.
- **Networking Tasks**: Wait for network services like DHCP or DNS to become active before connecting to network resources.
